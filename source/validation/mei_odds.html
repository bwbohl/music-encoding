TEI for authoring MEI ODD

Disclaimer

This customization is based on the TEI 4.9.0 release of the tei_odds.odd customization for authoring TEI ODDs and is being modified to accomodate the authoring of MEI ODD files.

Aside from the overdue modernization of the MEI ODDs Schema, a major reason for updating to tei:4.9.0 was the introduction of <constraintDecl> which allows Schematron query language binding and schematron namespace declarations.

Introduction

The definitions of both the Music Encoding Initiative (MEI) Guidelines and the Schemata are facilitated in so called One-Document-Does-it-all (ODD) syntax as defined by the Text Encoding Initiative (TEI) XML dialect. Because the specifications of the TEI dialect emcompass a vast amount of elements and attributes for various kinds of text markup, creating a subset for the purposes of the MEI definitions is strongly adviseable. This ‘customization’ is defined in the backmatter of this document. Moreover this document summarizes a set of editorial conventions for encoding the MEI Guidelines according th this schema.

The editorial conventions aim to produce markup that is parsimonious, semantic rather than presentational, and aligned with concrete downstream behaviors (rendering, glossary generation, indexing, cross-referencing, validation).

The guiding principle throughout: markup should earn its presence by enabling a behavior or capturing a distinction that matters. Tagging that does not achieve an effect is a cost without a benefit.

1. Encoding Levels and Rollout Plan

The encoding conventions are organized in five cumulative encoding levels. Each level is a enrichment of the previous one and augments the encoding to facilitate specific output intentions.

  1. Level 1 — Consistent baseline encoding. Apply the mei_odds schema to ensure a consistent structural encoding of the MEI specifications (aka source and guidelines).
  2. Level 2 — Bibliography. Introduce <bibl> and related elements; build a coherent bibliography that examples and prose can reference.
  3. Level 3 — Musical works and their authors. Tag musical works mentioned or used as examples (<title>, <persName>, with appropriatexml:lang), supporting indexing.
  4. Level 4 – Semantic sugar. Introduce and settle core distinctions of: <abbr> vs. <term> vs. <mentioned> vs. <name>/<orgName>/<persName> vs. <title>) and apply them consistently. Decide explicitly what is not tagged.
  5. Level 5 — Cross-referencing apparatus. Introduce <gloss> and <expan> with target/ref attributes for index generation, mouseover behaviors, and a unified glossary.

Encoding Level 1 should be achieved for MEI 6.0, all other levels are to be applied later and preferably step-by-step and consistently accross all MEI source files (docs nad modules) in the above order. The below encoding guidelines will illustrate the markup for Encoding Level 1, guidelines for the higher levels will be added when applicable.

2. Encoding Level 1

The main goal of Encoding Level 1 is consistency, including:

  • File preamble
  • Schema associations
  • Metadata in the headers
  • Markup of textstructures, e.g., <div> with <head> and <p>
  • Deprecation rend in favour of rendition or the TEI processing model
  • Deprecation of <abbr> for lexicalized Latin discourse markers such as ‘e.g.’ and ‘i.e.’
  • pureODD-markup of specifications, e.g., <elementSpec>

2.1. Encoding Guidelines Chapters

Each chapter of the guidelines is represented by one TEI document with <TEI> as root element. Consequently the file will contain <teiHeader> and <text> elements. While the header will be mostly identical in all chapters some metadata will be specific to the chapters:

Analytic title

Encoded in /TEI/fileDesc/titleStmt/title[level="a"]

Chapter editor

Encoded in /TEI/fileDesc/titleStmt/respStmt, e.g.:

The text of the chapter is to be encoded in <body> (/TEI/text/body). Although <front>, and <back> are also available in <text>, their use is discouraged in chapters.

The contents of the body have to start with a <div> holding a xml:id and a <head>, both of which hold the chapters heading. This should also be true for any subdivision of the chapter.

2.1.1. Creating Element or Attribute Overview-Lists

The MEI Guidelines contain overview lists of elements or attributes discussed or relevant in the respective section. These are encoded using the <specList> element with a child <specDesc> for each referenced element or attribute class. Attributes on the <specDesc> control, what to include, depending on the target type:

element
add the value of the element’s ident into key
attribute(s)
add the attribute classe’s ident into key and the ident values of all attributes from that class that you want to be listed as space-separated list into atts.

2.1.2. Encoding Code or Code References in the Textflow

Every mention of any elements, attributes, models, or datatypes from the MEI specifications in the MEI Guidelines should be tagged following the below scheme, to facilitate automatic linking between the Guidelines and the Specifications.:

Mentioning element names
<gi scheme="MEI">note</gi>
Mentioning attribute names
<att>pname</att>
Giving examples for attribute values
Isolated attribute values in the text have to be marked using the <val> element:
<val>c</val>

2.2. Encoding Figures – Notation Examples and Codeblocks

The Guidelines contain figures, such as notation examples from graphics files available in the repository, or generated on-build from MEI encodings with Verovio. Moreover, the code exmples can be rendered as codeblocks. Whichever you want to achieve, it must always be wrapped in a <figure> with a <head> encoding the figure caption ( without any prefix or numbering; theses will be generated automatically).

Appendix A Structural modifications

A major structural modification to the definition of this customization is moving the <schemaSpec> to the <back> to free the <body> and make space for a documentation of this ODD. Although not required by TEI it, makes for a clearer separation of the two.

Moreover, all the <moduleRef> elements have been moved into <specGrp> elements inside the respective sections in this documentation. This was done to facilitate accompanying the modification with some easier to read documentaiton and explanations. Theses definition now are included via <specGrpRef> elements into the <schemaSpec>.

  • Only include elements currently used in MEI module definitions and guidelines
  • Only include modules required due to elements, attribute classes or module classes they define

Please be aware that the following does not list all modules defined by the TEI all ODD but just those, that are still included in the MEI ODD schema or had been included in the preceeding version.

Appendix D A new module: xinclude

The mei-source.xml file relies on XInclude to reference the individual ODD files of the MEI Guidelines chapters and module definitions. To facilitate the validation of mei-source.xml even without active resolution of XInclude statements, the definition of the <include> element was borrowed from the TEI XInclude customization by the means of ‘ODD chaining’.

Because a stray element without module assignment did not seem adequate a corresponding xinclude module was added.

reference #add_element_xi-include
reference #mod_element_xi-include

The <include> element then was modified (and this is where the actual ‘ODD chaining’ happens), to be member of the xinclude module. Moreover the definition of the <include> element was drilled down to what is actually in use in the MEI ODD files:

  • available on the div-level, i.e., member of the model.divLike to allow inclusion of the guidelines chapters
  • available on the div-level, i.e., member of the model.oddRef to allow inclusion of the module definitions
  • no content, because MEI ODD files do not encode, e.g., a <fallback>
  • require the presence of a href
Element <include>change

Appendix E Future Considerations

The work on the MEI ODDs surfaced some ideas and future needs:

  • Improve bibliographic references and citation by allowing<bibl>, <cit> from the core module
  • Improve index generation by allowing <divGen> and adding some custom types to the XSLTs responsible for generating the guidelines
  • Improve encoding of terms by allowing <gloss>
  • Improve referencing values from code examples by allowing <mentioned>
  • Improve citeability by adding and implementing <citeStructure>
  • Improve encoding of tables by adding att.tableDecoration from the gaiji module
